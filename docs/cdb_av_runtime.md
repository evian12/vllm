# CDB-AV Runtime Contract

This document describes the persistent CDB-AV path in this branch. It is an
implementation contract, not a claim that GPU performance has already been
validated on every model or workload.

## 1. Request-level Draft length K

The server-side speculative-token limit is
`SpeculativeConfig.num_speculative_tokens`. For the current target
configuration, set it to **8**.

- `CDB_AV_K_POLICY=hf_confidence`: the server ignores a request's legacy
  `extra_args["cdb_draft_k"]` value and ignores `CDB_AV_FRESH_K`. The request
  can draft up to the server limit. After each candidate token, the Draft
  Worker computes the greedy-token probability
  `exp(max(logits) - logsumexp(logits))`. It retains that candidate and stops
  the request when the probability is strictly below
  `CDB_AV_HF_THRESHOLD`.
- `CDB_AV_K_POLICY=manual`: an explicit integer `cdb_draft_k` remains an
  optional upper bound for controlled comparisons.

Thus, in HF-confidence mode, old clients may still send K=1/2/3/4, but those
values do not constrain the server. Actual K is selected by confidence,
bounded by the server's maximum K.

## 2. Fixed Draft window H

`CDB_AV_WINDOW_H` is a fixed, configurable window length; the default is 8.
It counts Draft scheduling steps, not the number of tokens generated by one
request.

- A request may become Ready before H. It leaves the Active Draft batch but
  retains its Worker state and exclusive KV lease until the window boundary.
- If all current members become Ready early, the Worker emits idle barrier
  steps. These count toward H and do not launch an early Target verification.
- The CPU queue and the Worker both enforce the H boundary. The Worker rejects
  a boundary RPC unless exactly H steps have completed.
- A member admitted late in a window may remain unfinished at H. Its state is
  carried to the next window; its per-request K cap is not silently reduced to
  the remaining steps in the current window.

## 3. Ready queue and Target scheduling

Only a completed H boundary publishes its Ready records to the CPU-side Ready
queue. Current-window members remain in the lease set and cannot be selected
early.

Ready records from an earlier completed window remain eligible for Target
scheduling even while a later Draft window is open. The scheduler:

1. selects the oldest Ready requests by their `ready_at` timestamps, within
   the available `max_num_running_reqs` capacity;
2. keeps unselected Ready records queued and protected from preemption;
3. schedules each selected request only when all its Draft candidates fit in
   the current Target token budget; partial verification is rejected;
4. may batch selected Ready verification with unrelated AR or Prefill work.

There is no dynamic refill inside a Target verification forward. If the Ready
queue is larger than the available Target capacity, the remainder stays queued
for a later scheduling opportunity. Ready requests that cannot fit the current
token budget are skipped in favor of shorter Ready requests behind them. If a
request's full K+1 verification input cannot fit even in an otherwise empty
Target batch, it is not admitted to Draft and remains on native Target-only
generation instead of becoming permanently stuck in Ready.

## 4. Intra-window admission and packed Draft token budget

A new request becomes Draft-eligible only after Target has produced its first
output token and the request has a stable, Target-confirmed prefix.

With KV reuse enabled, new Prefill rows are packed with active one-token Draft
decode rows. Admission is bounded by the remaining Draft input-token budget:
the active decode rows reserve one token each, and planned Prefill suffixes
must fit in the remaining budget. For a cached request, the planned Prefill
cost is computed from the accepted-prefix reuse span rather than charging the
entire prompt again. The Worker also checks the actual input buffer capacity
before writing packed token IDs.

## 5. KV ownership and handoff

Draft KV pages are exclusive leases from the shared block pool and must not
overlap formal Target ownership. At H:

- Worker synchronizes and stages Ready records plus Carry snapshots;
- CPU validates the complete Ready/Carry partition, request provenance,
  window ID, token count, and lease ownership before publishing the batch;
- the complete Ready batch is sent to the Scheduler in one
  `DraftTokenIds` update;
- Ready leases are released or parked for KV reuse, while unfinished leases
  remain Carry.
- Shutdown preflights all CPU-owned blocks, requires the Worker reset ACK to
  match the exact active/cached request-ID set, and only then frees the pages.

Failed intra-window admission rolls back staged Worker members and CPU leases.
Shutdown releases persistent Worker state and CPU-owned leases.

## 6. Required and diagnostic environment

A persistent HF-confidence run should explicitly set:

```bash
CDB_AV_REFILL=1
CDB_AV_PERSISTENT=1
CDB_AV_K_POLICY=hf_confidence
CDB_AV_HF_THRESHOLD=0.4
CDB_AV_WINDOW_H=8
CDB_AV_STEP_MODE=1
CDB_AV_VARLEN=1
CDB_AV_SPLIT_RPC=1
CDB_AV_WORK_QUEUE=1
CDB_AV_KV_REUSE=1
CDB_AV_INTRA_WINDOW=1
CDB_AV_ALLOW_FRESH_WAITING=0
CDB_P1_VIRTUAL_H=0
```

For a diagnostic run, also set `CDB_AV_TRACE_STEPS=1`. Keep replay and
validation modes explicit; the reference experiment uses
`CDB_AV_REUSE_REPLAY=0`, `CDB_AV_REUSE_VALIDATE=0`, and
`CDB_AV_VALIDATE_METADATA=0`.

The vLLM speculative configuration must set
`num_speculative_tokens=8`; H=8 alone does not raise the server K limit.

## 7. Source checks and GPU acceptance

The branch CI compiles the CDB-AV runtime and test modules, runs the
dependency-free K/window/queue/token-budget policy tests, checks whitespace,
and runs Ruff's undefined-name check.

Before claiming a GPU runtime result, verify the server log contains:

- `p2_runtime_config` with `H=8`, `max_k=8`, and
  `k_policy=hf_confidence`;
- `CDB_HF_CONF` records showing per-request `K_cap=8`, varying
  `K_actual`, and `low_confidence` / `max_k` stop reasons;
- exactly eight Draft steps before each `p2_boundary`;
- Ready selection bounded by Target capacity, with deferred Ready records
  remaining queued;
- no lease-ownership, stale-context, partial-verification, or input-buffer
  capacity errors.

Source CI is not a substitute for the single-GPU end-to-end acceptance run.
